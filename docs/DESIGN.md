# 设计说明

## 线程模型

```
输入线程 ──────┐
               ├─→ EventBus ─→ 主循环 ─→ 绘制（上限 60 fps，实际事件驱动）
异步任务 ──────┘               │
                               └─→ 更新 AppState
音频线程 ─────────────────────────→ 原子量（position/duration/volume）
```

- **输入线程**只做 `event::read()`，把键盘与鼠标事件推进 channel，不做任何业务判断。
- **主线程**是唯一改状态的地方，因此不需要锁。
- **播放位置、时长、音量**通过 atomic 共享：主线程直接读，零分配、零锁。
- **Tokio 只开 2 个 worker**：并发上限恰好是「搜索 + 歌词 + 取 URL + 下载」这几条链。

## 低资源占用

实测口径（release 构建，CachyOS / Linux 7.2 x86_64，**112×34 终端**，`--no-tray`，从 `/proc/<pid>/status` 读 `VmRSS`；`--api native`，即接口在进程内运行，机器上没有 Node）：

| 场景 | 常驻内存 |
|---|---|
| 启动后空闲（未登录） | 19.1 MiB |
| 搜索之后 | 19.1 MiB |
| 播放中 | 19.1 MiB |
| 已登录（头像、会员信息、封面全部加载） | 21.5 MiB |

> 未登录与已登录的差别（19.1 对 21.5）来自**账号数据本身**：头像是解码后的位图，会员摘要与听歌时长也占空间。所以「空闲」的代价取决于是否登录、是否加载封面。
>
> 未登录空闲重复测三次：18.98 / 19.02 / 19.07 MiB，抖动约 0.1 MiB。

**与迁移前（`origin/main`，Node 后端）对比** —— 同机、同配置、同样 112×34 与 `--no-tray`，只有二进制变了：

| | 未登录空闲 | 已登录空闲 | 线程数 |
|---|---|---|---|
| 之前（`origin/main`，走本地 Node 服务） | 18.6 MiB | 20.2 MiB | 11 |
| 现在（`--api native`） | 19.1 MiB | 21.5 MiB | 12 |

**程序本身只涨约 0.3–0.4 MiB**（12 对 11 的线程差，加上内嵌 HTTP/TLS 客户端与 KRC 解密的常驻开销）。真正的收益在**进程之外**：迁移前必须常驻一个 Node 服务进程，而这个进程单独就占——

| 本地服务 | RSS |
|---|---|
| `node app.js --port=3000`（标准音源） | 42.5 MiB |
| `node app.js --port=3001`（概念版音源） | 66.9 MiB |

`--api native` 把这个进程整个去掉：`ps` 里不再有 node，程序也不再派生任何子进程（实测：子进程列表为空，`node app.js` 进程数前后不变）。所以按「整个播放器占多少」算，从 **60–86 MiB 降到约 19–21.5 MiB**；按「TUI 进程本身占多少」算，比迁移前多 0.3–0.4 MiB。

> **测量口径说明**：以上是 RSS（`VmRSS`）—— 进程映射的常驻物理页总量，含与其他进程共享的只读页（同一二进制跑多份会重复计入）。按 Pss（共享页按比例分摊）算，未登录空闲迁移前 12.5 MiB、现在 12.9 MiB；现在已登录 14.6 MiB。**两种口径一致：程序本身变化不到 0.5 MiB，收益来自去掉 Node 进程。**

**上表只在「播放小曲目」时成立。** 边下边播的字节缓冲**不留整首**：每个下载到的字节先写盘，内存只保留读指针附近的一段尾部窗口（上限 4 MiB，见下文「边下边播」）。所以常驻内存与曲目大小无关 —— 播一首 65 MiB 的 Hi-Res 也还是那几 MiB。实测：

| 场景 | 常驻内存 |
|---|---|
| 播放 64 MiB 曲目（修复前，整段缓冲留在内存） | 66.5 MiB |
| 同上（现在） | 12.5 MiB |
| 连续切 5 首、每首 64 MiB，下载都不取消（修复前） | 323.7 MiB |
| 同上（现在，切歌会取消下载） | 3.0 MiB |

这些数字来自 `streaming.rs` 中新旧两版实现在同一负载下的对比（单曲与切歌两种场景，读 `/proc/<pid>/status` 的 `VmRSS`/`VmHWM`）。

**二进制体积**（release、strip、`lto = "fat"`、`codegen-units = 1`）：

| 构建 | 体积 |
|---|---|
| 迁移前（`origin/main`） | 11,836,312 字节（11.29 MiB） |
| 现在，默认特性 | 12,261,728 字节（11.69 MiB） |
| 现在，`--no-default-features`（不含 Node 引导代码） | 12,195,608 字节（11.63 MiB） |

迁移净增约 **0.41 MiB**，来自内嵌的签名/加密/KRC/HTTP 栈；关掉 `node-bootstrap` 只省 0.06 MiB，因为引导代码很小（主要是字符串常量与几处 `Command` 调用）。

主要取舍：事件驱动而非忙轮询（主循环 `recv_timeout(tick)`，默认 200 ms）；音频全部写盘；下载进度每 256 KiB 才上报一次；不引入 `tracing` / `chrono` / `rand`，各自依赖树用几十行代码替代。

## 边下边播

取到播放直链后，**开头缓冲够就开始播**，其余在后台继续下载并缓存到磁盘。所以首播等待的是「缓冲开头」而不是「下完整首」；同一首第二次播直接命中磁盘缓存，零等待。

起播阈值是 `PREROLL_BYTES = 128 KB`（`src/audio/download.rs`）。这个数从等待时间倒推：常见码率 128 kbps ≈ 16 KB/s，128 KB 约 8 秒音频 —— 足够解码器稳定跑，等待又不至于被察觉。太小会反复卡顿；太大就退化成「下完才播」。

### 为什么要自定义缓冲

`rodio::Decoder<R>` 要求 `R: Read + Seek`（rodio 0.22 没有 `new_stream`），而网络流只能 `Read`、不能 `Seek`，没法直接喂进去。

`StreamingBuffer`（`src/audio/streaming.rs`）在内存里攒一个**会增长**的字节缓冲（但只留尾部窗口，见下），并在其上实现 `Seek`：读指针跑过已下载的部分时，**阻塞等待**后台下载线程补数据。解码器因此以为自己在读一个「很大的本地文件」，而数据其实还在路上。表现是——声音暂停，而不是提前结束。

阻塞有代价：`read()` 阻塞期间 rodio 的播放线程就停在那。所以每次等待都带 **15 秒超时** —— 真断网必须能报错退出，不能永远挂着。

### 内存开销：只留一个窗口，其余回读磁盘

缓冲**只留尾部窗口**（`MAX_KEPT_BYTES = 4 MiB`，回收到 1 MiB）。下载线程**先把每个 chunk 写入 `.part` 文件，再推进缓冲**，所以窗口之外的字节随时能从该文件 `pread` 回来（数据刚落盘，还在 page cache 里，代价接近一次 memcpy）。于是：

* 常驻内存与曲目大小解耦（见上表：64 MiB 曲目占 12.5 MiB，不是 66.5 MiB）；
* 往回 seek 到已回收的区域照样能播 —— 那部分在磁盘上，不报错。

回收为什么安全：**数据已经在磁盘上**，回收只丢掉内存里的副本。不回收也能跑，但那样播 Hi-Res 时 RSS 会随曲目大小线性增长（实测 1:1），与「常驻 20 MiB 以内」的定位直接冲突。

磁盘文件通过**已经打开的句柄**读，不按路径读：下载完成后文件会被改名成正式缓存文件，缓存回收也可能把它删掉，但只要句柄还活着，inode 就还在，数据仍可读。

### 流断了怎么办

读超时、下载失败、被取消 —— 三者都会让数据供给断掉。缓冲只如实记录状态（`is_finished` / `error` / `is_cancelled`），**不自己判定「这首放完了」** —— 那是播放引擎的事：rodio 把任何读错误都当 EOF 吞掉（symphonia 的 `format.next_packet().ok()?`），而「音源结束」既可能是真放完，也可能是流断了。两者混为一谈的具体后果：单曲循环（或队列里只有一首）会**从头再放一遍**，用户看到的就是「进度跳回开头」。

所以播放器空转时，引擎按流状态分四种处理：

| 流状态 | 结果 |
|---|---|
| 主动取消（用户切歌 / 停止） | 静默，不上报 |
| 已下载完整 | `TrackFinished`，主线程正常推进 |
| 未完成，有错误 | `Failed(reason)`：如实报错，**不切歌、不重放** |
| 未完成，无错误（读超时） | `StreamInterrupted { position }`：**保留位置**，主线程从该位置续播一次 |

位置必须在**曲目结束之前**记录：音源一结束，`Player::get_pos()` 就报 0，在那帧再读就把用户听到的位置抹掉了（`Runtime::last_position_ms` 就是为此存在）。

### 写 `.part`，不写最终文件名

两条下载路径都先写同目录下的 `.part`，**全部写完之后才改名**。边下边播尤其需要这样：一边下一边播，中途失败/取消是常态。直接写最终文件名会在磁盘上留下一个「看起来完整、其实只有半首」的文件，而 `cache.find` 只看「文件是否存在」—— 下次播就会命中它，莫名其妙地播到一半结束，单曲循环下还会一遍遍从头开始。

缓存回收与「清空缓存」都跳过 `.part`（它不是缓存，是半成品）；崩溃残留的 `.part` 在下次播该曲目时被 `truncate` 后复用。

## 接口适配

KuGouMusicApi 是逆向出来的封装，响应结构会漂移，而且**上游文档和实际行为**在不少地方对不上。本项目的做法是「多个候选键名 + 类型宽容 + 单个失败不拖垮整页」。以下是已对真实服务核实、与文档不符的地方：

| 上游文档说 | 实际 |
|---|---|
| `/login/qr/create` 返回 `qrcode` / `qrimg` | 返回 `data.url` / `data.base64` |
| 歌单广场在 `data.info` | 在 `data.special_list` |
| 歌手列表元素含 `songcount` | 该字段恒为 `0`，无法用于展示 |
| 歌手列表是扁平数组 | 实际嵌在 `data.info[].singer[]` |
| `/song/url` 返回 `data.url` | 实际在**顶层** `url` / `backupUrl`（数组），`data` 不存在 |
| 文档建议 `npm run dev` | 真正跑 `node app.js` 的是 `npm start` |

同一首曲目在搜索、歌单、排行榜三个接口里用**三套完全不同的字段名** —— 解析层最费工的部分，也是单元测试较多的原因：

| | 搜索 `/search` | 歌单 `/playlist/track/all` | 排行榜 `/rank/audio` |
|---|---|---|---|
| 标题 | `SongName` | `name`（带「Singer - 」前缀） | `songname` |
| hash | `FileHash` | `hash` | 顶层没有，在 `audio_info.hash_128` |
| 时长 | `Duration`（秒） | `timelen`（毫秒） | `audio_info.duration_128` |
| 专辑 | `AlbumName` | `albuminfo.name` | `album_info.album_name` |
| 歌手 | `Singer[]` | `singerinfo[]` | `authors[]` / `author_name` |

## 重试

读接口的瞬时失败会自动重试；写接口不重试。唯一判据是：**同一个请求再发一次，结果会不会不同**（`AppError::is_transient`）。

| 失败 | 重试 | 原因 |
|---|---|---|
| 连接被拒 / 连接重置 / 响应体读到一半断了 | 是 | 毫秒级返回，正是「网络通但打了个嗝」的样子 |
| HTTP 408 / 429 / 5xx | 是 | 对方明确表示「现在不行，晚点再来」 |
| **超时** | 否 | 已经等满 15 秒（连接超时 8 秒），说明对方卡住了而不是打嗝；再来两轮是拿用户的时间换一个大概率相同的结果 |
| 业务错误码（`error_code`） | 否 | 服务已响应，只是拒绝了这次请求；重发还是同一个答案 |
| 其他 4xx | 否 | 请求本身有问题（参数 / 鉴权），与时机无关 |
| 200 但响应体非 JSON | 否 | 内容问题；真正的截断会走传输错误，那是可重试的 |
| 写操作（收藏 / 取消收藏 / 删歌单 / 建歌单 / 领 VIP） | 否 | 重发可能改变结果：若 `/playlist/del` 第一次其实成功了、只是响应丢了，重发会得到「歌单不存在」 |

次数与间隔：**共 3 次（首次 + 2 次重试），间隔 300ms → 900ms**（×3 递增，不加抖动 —— 单用户本地客户端不存在「大量客户端同时重试」的问题）。所以一次打嗝最多多花用户 1.2 秒；再多就不是「扛过打嗝」，而是「卡着不报错」。

> 为什么值得做：取播放 URL 的路径会逐个尝试多个候选（hash, quality）组合；某个候选因为一次打嗝被跳过 —— 所有候选都打嗝之后 —— 用户看到的是「无可用播放地址（可能需 VIP 或已下架）」，**一个与真实原因毫无关系的结论**。
